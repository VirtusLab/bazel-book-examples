# PROJECT.scl Flagsets

This snippet pins how experimental project files behave on Bazel 9.1.0. It
backs {{3.2.7:ProjectSpecifications}}, and touches
{{3.2.1:BazelrcHierarchy}} and {{3.2.4:CommandLineFlags}} because project
enforcement judges flags from the command line and from rc files.

Each package has one `genrule`, `mode`, that writes `$(COMPILATION_MODE)` to
`bazel-bin/<package>/mode.txt`. Every project file here only sets
`--compilation_mode`, so `mode.txt` shows which flags actually reached the
target: `opt`, `dbg`, or Bazel's default `fastbuild`.

## What a project file looks like

- The file must be named exactly `PROJECT.scl`. For each top-level target,
  Bazel walks up from the target's package and uses the innermost
  `PROJECT.scl` it finds.
- The file must assign a top-level `project` variable. The helpers come from
  `project_proto.scl`, which you copy into your repository and load.
- Each `BuildableUnit` is a named flag set (a "config"). It has
  `target_patterns`, `flags`, an optional `description`, and `is_default`.
  When `--scl_config` is not set, Bazel applies the `is_default` unit whose
  `target_patterns` match the target. `--scl_config=<name>` picks a unit by
  name.
- `enforcement_policy` is set once for the whole project, not per unit. It
  takes `"warn"` (the default), `"compatible"`, or `"strict"`.
- Project flags must be output-affecting. A flag such as `--jobs` in a unit
  fails with `project flags don't support non-output affecting option`.

The protos in `src/main/protobuf/project/` in the Bazel repository define the
full schema, including `always_allowed_configs` and `project_directories`,
which this snippet does not use.

## Layout

| Path | Purpose |
| --- | --- |
| `project_proto.scl` | Helper constructors (`project_pb2`, `buildable_unit_pb2`), copied unchanged from Bazel |
| `warn/PROJECT.scl` | No `enforcement_policy`, so WARN. Units: `release` (default, `opt`) and `dev` (`dbg`) |
| `warn/nested/PROJECT.scl` | Nested project. Overrides `//warn:PROJECT.scl` for `//warn/nested` targets |
| `compatible/PROJECT.scl` | `enforcement_policy = "compatible"`, one default `release` unit |
| `strict/PROJECT.scl` | `enforcement_policy = "strict"`, one default `release` unit |
| `no_default/PROJECT.scl` | One `dev` unit without `is_default`, so `--scl_config` is required |
| `no_project/` | No `PROJECT.scl` above it |
| `lowercase/project.scl` | Wrong file name, so Bazel ignores it |
| `.bazelrc` | One `cquery`-only line that conflicts with the COMPATIBLE project |
| `tools/assert_project_scl.sh` | Runs every scenario and asserts output lines and `mode.txt` |

## Where `project_proto.scl` comes from

`project_proto.scl` is generated by Protolark from Bazel's
`src/main/protobuf/project/*.proto` files. Bazel's repository checks in the
generated file at
[`src/main/protobuf/project/project_proto.scl`](https://github.com/bazelbuild/bazel/blob/master/src/main/protobuf/project/project_proto.scl).
The copy here is unchanged from `master` at commit `3a07102` (October 2026),
including its `DO NOT EDIT` header. Bazel does not ship it as a loadable
module, so a repository that uses project files keeps its own copy.

## Behavior on Bazel 9.1.0

| Command | Result |
| --- | --- |
| `bazel build //warn:mode` | Applies `release`. `mode.txt` is `opt` |
| `bazel build //warn:mode --scl_config=dev` | Applies `dev`. `mode.txt` is `dbg` |
| `bazel build //warn:mode --define=x=1` | WARN lists `--define=x=1` and builds |
| `bazel build //warn:mode --compilation_mode=dbg` | WARN lists the flag, but the project wins. `mode.txt` is `opt` |
| `bazel build //compatible:mode --compilation_mode=dbg` | Fails: conflicts with the selected config |
| `bazel build //compatible:mode --define=x=1` | Warns only: the config does not set `--define` |
| `bazel build //compatible:mode --compilation_mode=opt` | Builds: the same value is not a conflict |
| `bazel cquery //compatible:mode` | Fails: the workspace `.bazelrc` line counts as a user flag |
| `bazel build //strict:mode` | Fails with no user flags (see the quirk below) |
| `bazel build //warn:mode --noenforce_project_configs` | Ignores project files. `mode.txt` is `fastbuild` |
| `bazel build //no_project:mode` | No project applies. `mode.txt` is `fastbuild` |
| `bazel build //warn:mode //no_project:mode` | Applies `release` to both targets |
| `bazel build //warn/nested:mode` | Applies `nested_debug` from the nested file. `mode.txt` is `dbg` |
| `bazel build //warn:mode //warn/nested:mode` | Fails: `Mismatching default configs for a multi-project build` |
| `bazel build //warn:mode --scl_config=nope` | Fails and lists valid configs with their descriptions |
| `bazel build //lowercase:mode` | No project applies. `mode.txt` is `fastbuild` (Linux) |
| `bazel build //no_default:mode` | Fails: no default config, so `--scl_config` is required |
| `bazel build //no_default:mode --scl_config=dev` | Applies `dev`. `mode.txt` is `dbg` |

For the same reason, `bazel build //...` fails: it mixes targets owned by
different project files.

### The workspace `.bazelrc` is not exempt

The enforcement messages say "command line or user bazelrc", and the
checked-in workspace `.bazelrc` counts as a user bazelrc. Its line here is
scoped to `cquery` so that only `bazel cquery //compatible:mode` sees it. As a
`build` line it would add to the warning of every build in the snippet. A line
behind a named config shows up in the warning by the config's name, such as
`'--config=ci'`, rather than by its expanded flags.

### The rules_python `--flag_alias` quirk

Even with an empty `MODULE.bazel`, Bazel 9.1.0's built-in `bazel_tools`
module pulls `rules_python@1.7.0` into the module graph (through `protobuf`
and others; see `bazel mod graph --include_builtin`). rules_python registers
flag aliases such as
`--flag_alias=build_python_zip=@@rules_python+//python/config_settings:build_python_zip`.
Project enforcement counts those as user flags. As a result:

- WARN and COMPATIBLE print the "also sets output-affecting flags" warning on
  every build, listing the `--flag_alias` entries plus any flags you passed.
- STRICT fails on every build, even with no user flags at all.

The `bazel build //strict:mode` command in `meta.yaml` is `expect: error` on
purpose. If it starts succeeding on a newer Bazel, the quirk is fixed and the
article should be updated.

## Run it

```bash
cd knowledge/examples/snippets/project-scl-flagsets
bazel build //warn:mode && cat bazel-bin/warn/mode.txt
bash tools/assert_project_scl.sh
```
